# ADR-0008 — Externally derived `x`, and the SRP-6a construction Chiavora ships

Status: Accepted · 2026-09-14

## Context

ADR-0007 chose SRP-6a. RFC 5054 computes `x = SHA1(s | SHA1(I | ":" | p))`, with
no password stretching; Chiavora derives `x` from `rootKey` instead, which is a
deviation the first ground rule requires written down. The security design names
no hash for SRP, no login identifier, and no unknown-identifier behaviour for
the login exchange.

## Decision

Only `x`'s provenance changes. The exchange (`A`, `B`, `u`, `S`, `M1`, `M2`) is
RFC 5054's, unmodified, over the 4096-bit group with SHA-256.

## 2. The deviation

`srpX = HKDF-SHA256(rootKey, "chiavora-srp", 32)`, the MUK's sibling, and `x` is
built from it (§3.3). This is not a weakening: RFC 5054's `x` is one SHA-1 of the
password, while ours descends from Argon2id (`m = 256 MiB, t = 4, p = 4`) and
the 128-bit Secret Key (ADR-0007 §3.1).

### 2.2 Where the removed inputs go

- The password: `Argon2id(password, salt)` inside `rootKey`.
- The identity `I`: `accountId`, in the HKDF `info` strings
  `"chiavora-salt|" ‖ accountId` and `"chiavora-skk|" ‖ accountId`. A
  transplanted `v` still needs the original account's password and Secret Key.
- The salt `s`: the Argon2id salt derived from `accountSalt`, plus `srpSalt`.

## 3.3 The SRP salt and the hashes

```text
x = SHA-256(srpSalt ‖ srpX)        // H_x: fixes every stored verifier
k = SHA-256(N ‖ PAD(g))            // H_proto, and u, M1, M2: nothing stored
```

`srpSalt` is 256 bits, client-generated by CSPRNG at signup on ADR-0005's
pattern, sent at enrollment, stored as-is and served as SRP's `s`. It adds no
entropy. It is structural: it keeps SRP's shape and a canonical library's
`(s, v)` interface. It freezes at the first verifier registration, which an
offline account never makes.

## 4. What RFC 5054's vectors establish

1. The group parameters are the right bytes: `N` and `g` against Appendix A.
   Reaches the shipping 4096-bit group.
2. The exchange algebra given `x`: Appendix B, 1024-bit with SHA-1. Does not
   reach what ships.
3. `x`'s derivation and the algebra at the shipping instantiation: project
   vectors. Nothing published reaches it.

The implementation is generic over group and hash at compile time. The shipping
build has one instantiation; 1024-bit/SHA-1 exists only under `#[cfg(test)]`,
and SHA-1 is a dev-dependency, never a dependency.

## 5. The login identifier

An email, mapped server-side to `accountId`: a lookup key, never a KDF input.
Changing it changes no key material.
The pre-auth endpoint returns `accountSalt` and the Argon2id parameters, not
`accountId`.

### 5.2 `I` is `accountId`

`I` in the proof transcript is `accountId`, never the email. Nothing stored
depends on `M1`, so this is reversible.

### 5.3 Normalisation

Split at the last `@` and ASCII-lowercase the part after it; non-ASCII bytes pass
through, and the local part is untouched (RFC 5321). With no `@` the whole string
is the key. One total function serves signup, login lookup and §6, and is
registered as a parser of attacker input.

## 6. Unknown identifiers

The server simulates an account, following RFC 5054 §2.5.1.3.

### 6.2 The fake verifier

```text
seedKey                       // 256-bit server secret, per deployment, never served
e        = normalise(email)   // §5.3
srpSalt' = HMAC-SHA256(seedKey, "chiavora-srp-fake-salt" ‖ e)
x'       = HMAC-SHA256(seedKey, "chiavora-srp-fake-x"    ‖ e)
v'       = g^x' mod N
```

The server then proceeds exactly as for a real account, and `M1` fails as for a
wrong password. The pre-auth endpoint derives `accountSalt'` and Argon2id
parameters within the I4 floor from the same `seedKey` and `e`.

## Consequences

- There is no unknown-account branch after the lookup, so timing holds by
  structure. The enumeration test covers the parameter fetch and the exchange.
- One seed key backs both oracles: losing it opens both, and rotating it
  changes every fake response.
- A hostile server can choose `accountSalt` and the Argon2 parameters. That only
  wastes a derivation on the client; it is recorded, not defended against.
- `User@example.com` and `user@example.com` are different accounts, and
  internationalised addresses are not normalised.

## Alternatives considered

- `x = srpX` with no `srpSalt`: a second, structural deviation that changes the
  message flow.
- A random `B` for unknown identifiers: skips the modular exponentiation, so the
  response returns measurably sooner.
- The RFC's `HMAC-SHA1`: SHA-1 is not in the primitive set.
